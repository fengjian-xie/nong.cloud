# 乡桥多角色工作台与共用架构

## 建议：一套平台底座，按角色组合工作台

无需为每个角色建设独立后端、独立数据库和独立账号体系。第一期采用模块化单体：沿用仓库现有React前端与Java后端，按业务领域组织模块。角色数量不是拆分微服务的依据。

平台主体为乡桥农业有限公司，福安运营服务主体为福安市乡桥农事综合服务有限公司。nong.cloud为农事中心首页，m.nong.cloud为管理后台，work.nong.cloud为用户工作台，nc.nong.cloud承载经授权公开的生产展示、故事和消费者认购入口，api.nong.cloud为开放API。各入口可以消费同一套受控业务接口，但消费者端不得直接读取内部记录、家庭授权和私有成本。旧农事品牌域名弃用。

一个账号可属于多个经营主体、拥有多个被授权角色。例如合作社同时提供农资、农服与植保服务，工作人员登录后选择当前主体与工作身份，不必重复注册。业务模块共用，数据与操作权限不共用。

## 已实现的前端原型

入口：`/workspaces`；角色工作台：`/workspace/:role`。现有运营后台保持原路由。

| 工作身份 | 路由角色 | 业务模块与专用内容 |
| --- | --- | --- |
| 种植户 | farmer | 自有地块、原始记录、卡片、私人成本、委托服务、供货意向、肥力、家庭授权 |
| 合作社 | cooperative | 授权社员地块与卡片、记录协同、代预约、集体供货、本主体货权库存 |
| 采购商 | buyer | 主动公开的成熟货源、本主体采购需求、共享库存预订、年会员或按条查看 |
| 农资商 | supplier | 模拟NFC识别、农户本次交易授权、商品批次与数量、销售凭据 |
| 农机手 | machine | 指派订单、接单、作业与完工、自有农机状态 |
| 农服队 | team | 同一服务流程、队伍资源、委托方验收 |
| 植保团队 | protection | 同一服务流程，另加药剂批次、施用总量与单位、面积、标签安全间隔、专业核对记录 |
| 冷库 | warehouse | 本库保管批次、锁定订单交接、电力与温湿度接入规划 |
| 加工分拣 | processor | 本主体货权库存、分级投入产出平衡、损耗、B级货补货需求 |
| 检测机构 | lab | 本机构委托、采样、检测结果、PDF元数据、提交待运营核验 |
| 子女代办 | family | 授权查看、额外授权后卡片代办、农场故事草稿；不得自行提权 |

共11个业务角色、38个业务页面入口、11个角色概览，另有角色入口页和原运营后台。各角色复用页面壳、表格、对话框、表单与业务组件，不复制11个项目。

当前角色是固定演示身份，切换器不是正式鉴权。操作保存本机演示日志；不可写缓存时仅保留当前会话。不要在演示中输入真实个人信息。模型选择器仅用于前端展示边界，所有示例数据仍属于本机原型，不能据此声称具备生产级数据隔离。

## 共用与独立的边界

| 共用模块 | 不同角色的差异 |
| --- | --- |
| 账号、主体与授权 | 同一账号的角色、所在组织、数据关系、委托有效期不同 |
| 地块、产季、原始采集事件 | 农户看自己；合作社看获授权社员；服务方只看履约必要资料 |
| 农事卡与版本同步 | 同一张卡；本人、合作社与子女的管理权限不同 |
| 服务订单与作业凭据 | 农机、农服、植保共用状态机；专业字段按服务类型扩展 |
| 产品、货源、批次与库存 | 公开供货意向、货权、保管权、采购订单权限分开 |
| 资料存储、消息与审计 | 共用技术服务；访问与下载按业务对象逐项校验 |

通用服务流程：待接单 → 已接单 → 作业中 → 待验收 → 已完成。待接单/已接单可由委托方取消；服务方不能自验收。植保施用订单缺少专业作业档案时不能提交完工；纯巡检等不同服务类型后续应配置不同的凭据要求，不强迫记录不存在的施用。

农资购买凭据只证明购买，不自动转成地块施用事件。服务完工记录只证明履约进度，不自动判定记录认证或产品质量。检测机构不能审核自己的报告。分拣产出未验收前不重复生成可售库存。冷库有保管权不代表有货权；电力活动不能证明货量或品质。

## 正式后端的授权与数据结构建议

仓库现有`accounts.role`为单值，通用`entities`已有`owner_id`、`organization_id`与版本字段，另有幂等与审计表。本轮未修改后端，也未让现有单角色字段自动获得多角色能力。正式对接时应增加关系结构，而不是将演示角色参数当成可信登录身份。

建议增加：

- `organizations`：经营主体、县域运营归属、主体类型、核验状态。
- `organization_memberships`：账号在主体中的身份与有效期。
- `roles`、`permissions`、`role_permissions`、`account_role_assignments`：支持一个账号在不同主体拥有多个角色。
- `delegations`：委托人与被委托人、操作范围、对象范围、同意凭据、生效/失效与撤销时间。
- `plot_authorizations`：地块权利人与合作社、受托服务方之间的授权关系。
- 专用业务表：服务订单/履约事件/植保明细、农资销售及关联凭据、供货发布快照、采购意向、库存账本、分拣投入产出、样品/报告/独立核验、私人成本估算。

县域租户、经营主体、地块权利人不是同一个概念，不能只按县域过滤后就放开全部农户数据。服务端每次请求同时检查：登录身份、当前主体成员资格、角色操作权限、对象归属或有效委托、状态流转与版本。采购接口只返回允许公开的投影字段；隐藏按钮不能保护已经返回到浏览器的私有数据。

数据敏感规则：

- 农户私人成本、家庭信息、原始GPS坐标不提供给采购商。
- 服务商只获得受托订单必要的地块与联络信息；结束后的保留/访问期限另行规定。
- NFC读卡不授予全档案读取权，关联交易需一次性确认和最小必要身份返回。
- 子女授权需本人验证，撤销后阻断接口并清除该身份的前端数据缓存。
- 消费者只读取另行授权的公开生产摘要；故事和媒体发布需独立确认。

## 对接顺序

1. 建立主体、多角色身份和授权关系，补齐服务端对象级访问测试；入口由可信会话返回。
2. 优先打通种植户—合作社—农服/植保：申请、指派、接单、凭据、本人验收。
3. 接入工程样卡协议：设备身份、签名/校验、事件序号、配置版本、蓝牙回执、重传去重；NFC公开标识与私有日志分开。
4. 接入农资销售凭据与实际施用的关联，不自动合并二者；建立争议更正而不覆盖原始事件。
5. 接入检测报告的真实附件、独立核验与地块肥力档案，再进入乡桥记录体系核验流程。
6. 将供货发布、库存预订、分拣投入统一到事务化库存账本，锁定数量、幂等请求、版本冲突与释放时限由服务端执行。
7. 接入实际会员权益、支付、合同和授权联络；生产端不收平台服务费。
8. 按县域复制经营配置、专业服务类型和授权规则，再逐步扩展地区，不按角色复制数据库。

## 本轮的功能界限

已有原运营页面与新增角色页面共用农事卡、地块、库存等演示数据。新服务订单、销售凭据、检测委托、家庭授权、故事及分拣记录保存在独立的版本化角色演示日志中。检测委托提交暂未自动变成原运营“土壤肥力”的归档报告；机构报告、专业凭据、私人成本也未自动进入外部报送。

真实账号多角色授权、硬件/NFC/蓝牙/GPS、GIS测绘、实际文件存储、支付、用电遥测、摄像头、一品一码及消费者端发布接口均尚未接入。演示库存以2026-08-29为基准；正式预订必须按当前时间和真实品质校验有效期。前端局部业务校验不能替代服务端事务、并发控制与不可篡改审计。
